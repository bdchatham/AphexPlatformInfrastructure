# Authentik Identity Provider

This directory contains Kubernetes manifests for Authentik, the primary Identity Provider (IdP) for the platform. Authentik provides a web UI for user and group management, OIDC provider capabilities, and integration with external identity providers.

## Overview

Authentik is deployed as two components:

- **Server**: Handles web UI, API, and authentication flows
- **Worker**: Processes background tasks (email, webhooks, etc.)

Both components share the same configuration and connect to PostgreSQL for data storage.

## Manifests

- `server-deployment.yaml`: Authentik server deployment
- `worker-deployment.yaml`: Authentik worker deployment
- `service.yaml`: Kubernetes service for Authentik server
- `blueprints-configmap.yaml`: Authentik Blueprints for automated configuration
- `secret.yaml.example`: Example secret template (not committed to Git)

## Authentik Blueprints

Authentik Blueprints are **declarative YAML configuration files** that Authentik auto-applies on startup. They enable fully automated bootstrap without manual UI configuration.

### What Blueprints Configure

The `blueprints-configmap.yaml` defines:

1. **Initial Groups**:
   - `admins`: Superuser group with full platform access
   - `engineering`: Standard user group with read-only access

2. **Initial Admin User**:
   - Username: `admin`
   - Email: `admin@platform.local`
   - Password: Set via Kubernetes Secret (generated by bootstrap)
   - Assigned to `admins` group

3. **OIDC Provider for Dex**:
   - Name: "Dex OIDC Provider"
   - Client ID: `dex-client`
   - Client Type: Confidential
   - Redirect URIs: `https://dex.home.local/callback`
   - **Note**: Client secret is set by Config Sync Job, not Blueprint

4. **Platform Services Application**:
   - Slug: `platform-services`
   - Name: "Platform Services"
   - Linked to Dex OIDC provider

### Blueprint Structure

Blueprints use Authentik's declarative model format:

```yaml
version: 1
metadata:
  name: Initial Platform Setup
entries:
  # Create group
  - model: authentik_core.group
    identifiers:
      name: admins
    attrs:
      is_superuser: true
  
  # Create user
  - model: authentik_core.user
    identifiers:
      username: admin
    attrs:
      name: Platform Administrator
      email: admin@platform.local
      is_active: true
      groups:
        - !Find [authentik_core.group, [name, admins]]
  
  # Create OIDC provider
  - model: authentik_providers_oauth2.oauth2provider
    identifiers:
      name: Dex OIDC Provider
    id: dex-provider
    attrs:
      authorization_flow: !Find [authentik_flows.flow, [slug, default-authentication-flow]]
      client_type: confidential
      client_id: dex-client
      redirect_uris: |
        https://dex.home.local/callback
      signing_key: !Find [authentik_crypto.certificatekeypair, [name, authentik Self-signed Certificate]]
      property_mappings:
        - !Find [authentik_providers_oauth2.scopemapping, [scope_name, openid]]
        - !Find [authentik_providers_oauth2.scopemapping, [scope_name, email]]
        - !Find [authentik_providers_oauth2.scopemapping, [scope_name, profile]]
  
  # Create application
  - model: authentik_core.application
    identifiers:
      slug: platform-services
    attrs:
      name: Platform Services
      provider: !KeyOf dex-provider
```

### Blueprint Syntax

**Model References**:
- `model`: Authentik model type (e.g., `authentik_core.user`)
- `identifiers`: Unique fields to identify existing objects
- `attrs`: Attributes to set on the object

**Special Operators**:
- `!Find [model, [field, value]]`: Find existing object by field value
- `!KeyOf id`: Reference object by ID defined earlier in blueprint
- `!Format [template, args]`: Format string with arguments

### Blueprint Volume Mount

Blueprints are mounted as a ConfigMap volume:

```yaml
volumeMounts:
  - name: blueprints
    mountPath: /blueprints/custom
    readOnly: true

volumes:
  - name: blueprints
    configMap:
      name: authentik-blueprints
```

Authentik auto-discovers and applies all YAML files in `/blueprints/custom/` on startup.

## Modifying Blueprints

To modify Authentik configuration via Blueprints:

### Adding a New Group

1. Edit `blueprints-configmap.yaml`
2. Add new group entry:
   ```yaml
   - model: authentik_core.group
     identifiers:
       name: developers
     attrs:
       is_superuser: false
   ```
3. Commit and push to Git
4. ArgoCD syncs changes automatically
5. Restart Authentik pods to apply:
   ```bash
   kubectl rollout restart deployment/authentik-server -n auth-system
   kubectl rollout restart deployment/authentik-worker -n auth-system
   ```

### Adding a New User

1. Edit `blueprints-configmap.yaml`
2. Add new user entry:
   ```yaml
   - model: authentik_core.user
     identifiers:
       username: developer1
     attrs:
       name: Developer One
       email: developer1@platform.local
       is_active: true
       groups:
         - !Find [authentik_core.group, [name, developers]]
   ```
3. Commit and push to Git
4. ArgoCD syncs changes
5. Restart Authentik pods

**Note**: For production, prefer creating users via Authentik UI rather than Blueprints. Blueprints are best for initial setup and group definitions.

### Adding a New OIDC Application

1. Edit `blueprints-configmap.yaml`
2. Add new OIDC provider:
   ```yaml
   - model: authentik_providers_oauth2.oauth2provider
     identifiers:
       name: New Service OIDC Provider
     id: new-service-provider
     attrs:
       authorization_flow: !Find [authentik_flows.flow, [slug, default-authentication-flow]]
       client_type: confidential
       client_id: new-service-client
       redirect_uris: |
         https://new-service.home.local/callback
       signing_key: !Find [authentik_crypto.certificatekeypair, [name, authentik Self-signed Certificate]]
       property_mappings:
         - !Find [authentik_providers_oauth2.scopemapping, [scope_name, openid]]
         - !Find [authentik_providers_oauth2.scopemapping, [scope_name, email]]
         - !Find [authentik_providers_oauth2.scopemapping, [scope_name, profile]]
         - !Find [authentik_providers_oauth2.scopemapping, [scope_name, groups]]
   ```
3. Add new application:
   ```yaml
   - model: authentik_core.application
     identifiers:
       slug: new-service
     attrs:
       name: New Service
       provider: !KeyOf new-service-provider
   ```
4. Commit and push to Git
5. ArgoCD syncs changes
6. Restart Authentik pods

## External URL Requirements

**CRITICAL**: All redirect URIs in Blueprints must use **external hostnames** that user browsers can reach, NOT internal Kubernetes DNS names.

### Correct (Browser-Reachable)

```yaml
redirect_uris: |
  https://dex.home.local/callback
  https://new-service.home.local/callback
```

### Incorrect (Browser Cannot Reach)

```yaml
# ❌ DO NOT USE
redirect_uris: |
  http://dex.auth-system.svc.cluster.local:5556/callback
  http://localhost:8080/callback
```

### Why External URLs Matter

OIDC authentication requires redirect URIs that user browsers can reach:

1. User accesses service at `https://service.home.local`
2. Service redirects to Authentik at `https://auth.home.local`
3. User logs in to Authentik
4. Authentik redirects back to service at `https://service.home.local/callback`

If redirect URIs use internal DNS names, the browser cannot reach them and authentication fails.

### Configuring External URLs

Replace `home.local` with your actual domain in all redirect URIs:

```yaml
# For homelab with .home.local domain
redirect_uris: |
  https://dex.home.local/callback

# For custom domain
redirect_uris: |
  https://dex.example.com/callback
```

Ensure DNS is configured so that `*.home.local` (or your domain) resolves to your Ingress controller's IP address. See `platform/auth/ingress/README.md` for DNS setup instructions.

## Configuration

### Environment Variables

Authentik is configured via environment variables:

**Database Connection**:
- `AUTHENTIK_POSTGRESQL__HOST`: PostgreSQL hostname (default: `postgresql.auth-system.svc.cluster.local`)
- `AUTHENTIK_POSTGRESQL__NAME`: Database name (default: `authentik`)
- `AUTHENTIK_POSTGRESQL__USER`: Database user (default: `authentik`)
- `AUTHENTIK_POSTGRESQL__PASSWORD`: Database password (from Secret)

**Authentik Settings**:
- `AUTHENTIK_SECRET_KEY`: Secret key for encryption (from Secret)
- `AUTHENTIK_ERROR_REPORTING__ENABLED`: Disable error reporting (default: `false`)
- `AUTHENTIK_LOG_LEVEL`: Log level (default: `info`)
- `AUTHENTIK_BLUEPRINTS__ENABLED`: Enable blueprints (default: `true`)

**Redis (Optional)**:
- `AUTHENTIK_REDIS__HOST`: Redis hostname (default: `redis.auth-system.svc.cluster.local`)

### Resource Limits

**Server**:
- Requests: 500m CPU, 512Mi memory
- Limits: 2000m CPU, 2Gi memory

**Worker**:
- Requests: 250m CPU, 256Mi memory
- Limits: 1000m CPU, 512Mi memory

Adjust these values based on your cluster capacity and usage patterns.

### Health Checks

**Liveness Probe**:
- HTTP GET `/api/v3/root/config/` on port 9000
- Initial delay: 30 seconds
- Period: 10 seconds

**Readiness Probe**:
- HTTP GET `/api/v3/root/config/` on port 9000
- Initial delay: 10 seconds
- Period: 5 seconds

## Post-Bootstrap Configuration

After bootstrap completes and Authentik is running, you can configure additional settings via the web UI.

### Accessing Authentik UI

1. Ensure DNS is configured (see `platform/auth/ingress/README.md`)
2. Open `https://auth.home.local` in browser
3. Accept certificate warning (if using self-signed certificates)
4. Retrieve admin password:
   ```bash
   kubectl get secret authentik-secrets -n auth-system \
     -o jsonpath='{.data.admin-password}' | base64 -d
   ```
5. Login with username `admin` and retrieved password

### Changing Admin Password

1. Navigate to **Directory** → **Users**
2. Click on `admin` user
3. Click **Set password**
4. Enter new password
5. Click **Update**

### Creating Additional Users

1. Navigate to **Directory** → **Users**
2. Click **Create**
3. Fill in user details:
   - Username (required, unique)
   - Email (required, unique)
   - Name (display name)
   - Password (or send password reset email)
4. Assign user to groups (`admins` or `engineering`)
5. Click **Create**

User can authenticate immediately - no pod restarts required.

### Configuring External Identity Providers

#### GitHub OAuth

1. Create GitHub OAuth App:
   - Go to GitHub Settings → Developer settings → OAuth Apps
   - Click **New OAuth App**
   - Application name: `Platform Services`
   - Homepage URL: `https://auth.home.local`
   - Authorization callback URL: `https://auth.home.local/source/oauth/callback/github/`
   - Copy Client ID and Client Secret

2. Configure in Authentik UI:
   - Navigate to **Directory** → **Federation & Social login**
   - Click **Create** → **GitHub**
   - Enter Client ID and Client Secret
   - Configure organization/team filtering (optional)
   - Map GitHub teams to Authentik groups
   - Click **Create**

3. Test:
   - Logout of Authentik
   - Click **Login with GitHub** on login page
   - Authorize application
   - User is created in Authentik with mapped groups

#### LDAP

1. Navigate to **Directory** → **Federation & Social login**
2. Click **Create** → **LDAP**
3. Configure LDAP server details:
   - Server URI: `ldap://ldap.example.com`
   - Bind DN and password
   - Base DN for user search
   - User and group filters
4. Map LDAP attributes to Authentik user fields
5. Click **Create**

#### SAML

1. Navigate to **Directory** → **Federation & Social login**
2. Click **Create** → **SAML**
3. Configure SAML IdP details:
   - Metadata URL or upload metadata XML
   - Entity ID
   - SSO URL
   - Attribute mappings
4. Click **Create**

## Troubleshooting

### Authentik Pod Fails to Start

**Symptom**: Authentik pod crashes repeatedly

**Possible causes**:
1. PostgreSQL not ready
2. Missing secrets
3. Invalid configuration

**Resolution**:
```bash
# Check pod logs
kubectl logs -n auth-system deployment/authentik-server

# Check PostgreSQL is running
kubectl get pods -n auth-system -l app=postgresql

# Check secrets exist
kubectl get secrets -n auth-system

# Verify database connection
kubectl exec -it deployment/authentik-server -n auth-system -- \
  psql -h postgresql.auth-system.svc.cluster.local -U authentik -d authentik
```

### Authentik Cannot Connect to PostgreSQL

**Symptom**: Authentik logs show "connection refused" or "authentication failed"

**Resolution**:
```bash
# Verify PostgreSQL is running
kubectl get pods -n auth-system -l app=postgresql

# Check PostgreSQL service
kubectl get svc postgresql -n auth-system

# Test DNS resolution
kubectl exec -it deployment/authentik-server -n auth-system -- \
  nslookup postgresql.auth-system.svc.cluster.local

# Verify credentials
kubectl get secret authentik-postgresql -n auth-system \
  -o jsonpath='{.data.postgresql-password}' | base64 -d
```

### Blueprints Not Applied

**Symptom**: Initial admin user or groups not created

**Resolution**:
```bash
# Check if blueprints ConfigMap exists
kubectl get configmap authentik-blueprints -n auth-system

# Check if blueprints are mounted
kubectl describe pod -n auth-system -l app=authentik-server | grep -A 5 blueprints

# Check Authentik logs for blueprint errors
kubectl logs -n auth-system deployment/authentik-server | grep -i blueprint

# Restart Authentik to reapply blueprints
kubectl rollout restart deployment/authentik-server -n auth-system
kubectl rollout restart deployment/authentik-worker -n auth-system
```

### OIDC Provider Not Working

**Symptom**: Dex cannot connect to Authentik OIDC provider

**Resolution**:
```bash
# Check OIDC discovery endpoint
curl https://auth.home.local/application/o/dex/.well-known/openid-configuration

# Check if OIDC provider exists in Authentik UI
# Login to Authentik → Applications → Providers → Dex OIDC Provider

# Verify client secret is set
# (Config Sync Job should have set this)

# Check Config Sync Job logs
kubectl logs -n auth-system job/auth-config-sync
```

### User Cannot Login

**Symptom**: User enters correct credentials but login fails

**Possible causes**:
1. User account disabled
2. User not in any groups
3. Database connection issues

**Resolution**:
```bash
# Check user status in Authentik UI
# Login to Authentik → Directory → Users → Select user
# Verify "Active" checkbox is checked

# Check user groups
# Ensure user is assigned to at least one group

# Check Authentik logs
kubectl logs -n auth-system deployment/authentik-server | grep -i error
```

## Maintenance

### Upgrading Authentik

1. Update image version in `server-deployment.yaml` and `worker-deployment.yaml`
2. Commit and push to Git
3. ArgoCD syncs changes automatically
4. Authentik pods restart with new version

**Note**: Check Authentik release notes for breaking changes and migration steps.

### Backing Up Authentik Data

Authentik data is stored in PostgreSQL. Back up the database:

```bash
# Create backup
kubectl exec -it postgresql-0 -n auth-system -- \
  pg_dump -U postgres authentik > authentik-backup.sql

# Restore backup
kubectl exec -i postgresql-0 -n auth-system -- \
  psql -U postgres authentik < authentik-backup.sql
```

### Scaling Authentik

For production environments with high load:

```bash
# Scale server replicas
kubectl scale deployment authentik-server -n auth-system --replicas=3

# Scale worker replicas
kubectl scale deployment authentik-worker -n auth-system --replicas=2
```

Update `server-deployment.yaml` and `worker-deployment.yaml` to persist changes.
